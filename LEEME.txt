RESOLVER-AR — PLATAFORMA WEB + BOT (fases 1-6)
==============================================

QUÉ ES
------
Una sola aplicación con dos interfaces (web y bot de Telegram) sobre la misma
lógica (lib/) y la misma base (datos/stock.db). Vendedores se registran con
invitación, ven el stock enmascarado, reservan, pagan, tienen 15 minutos para
verificar y pueden reclamar. El admin gestiona stock, precios, usuarios,
recargas, reclamos, auditoría y checker.

ROLES
-----
  admin     todo (usuarios, precios, reclamos, auditoría)
  operador  panel, stock, recargas, reclamos, checker (2FA obligatorio)
  vendedor  catálogo, saldo, reservas, recargas, bot
  checker   reservado para el verificador

RUTAS WEB
---------
  /login                 entrar (usuario + clave, luego TOTP si está activo)
  /registro?codigo=...   alta de vendedor con invitación (queda pendiente)
  /mi                    cuenta, 2FA, Telegram, sesiones, saldo
  /catalogo              catálogo, reservas, pago, countdown, recargas
  /panel/                stock (market, reservadas, vendidas, movimientos, cargar)
  /panel/admin.html      resumen, reclamos, checker, precios, usuarios, auditoría, lotes
  /panel/vendedores.html redirige a admin.html
  /login?token=...       NO: el token de servicio va como ?token= en las rutas API/panel

    GET  /api/admin/metricas
    GET  /api/admin/reclamos

    GET  /api/admin/usuarios ; POST /api/admin/usuarios/:id/estado | rol
    GET  /api/admin/auditoria | lotes

  SERVICIO (token)
    Igual que antes: /health /stats /ficha /lote /titulares /stock/* ... con
    ?token=<RESOLVER_TOKEN> o Authorization: Bearer.

BOT DE TELEGRAM
---------------
  /vincular <codigo>   código generado en /mi (una sola vez)
  /stock               disponibles por BIN y precio
  /pedir <bin> [n]     reserva, revela número + titular + countdown
  /mis                 reservas con cuenta regresiva
  /pagar <grupo>       confirma pago (no recobra)
  /datos <codigo>      número completo y titular
  /ok <codigo>         verificación OK (se ve en la web)
  /falla <codigo> [motivo]  crea reclamo
  /saldo               saldo y movimientos
  /desvincular
  Los chats vinculados a vendedores NO acceden a comandos de administración.
  Avisos: reserva asignada, por vencer, pago, venta OK, recarga, reclamo.
  Canal de auditoría: TELEGRAM_AUDIT (o el primer chat de TELEGRAM_ALLOW).

REGLAS CLAVE
------------
  - La cuenta es una sola para web y bot (vinculación por código).
  - El número completo solo se revela al vendedor asignado; el catálogo y los
    avisos usan máscara.
  - Toda reserva es transaccional (BEGIN IMMEDIATE + UPDATE ... WHERE estado).
  - El saldo se debita al reservar; pagar no vuelve a cobrar.
  - Impaga vencida: vuelve a DISPONIBLE y se devuelve el saldo.
  - Pagada vencida: pasa a VENDIDA (auto-OK).
  - Toda transición de estado y toda acción de stock/saldo/usuario se audita.
  - El ledger no se edita: cada movimiento agrega una fila con saldo_post.
  - Precio: vendedor > tramo por cantidad > precio de la tarjeta > BIN.
  - Checker: proveedor 'manual' por defecto; para integrar uno externo,
    registrarProveedor(nombre, fn) y setear CHECKER_PROVEEDOR=nombre.

      hay copia de hoy / de <7 dias, se omite. Forzar: --stock / --padron.
